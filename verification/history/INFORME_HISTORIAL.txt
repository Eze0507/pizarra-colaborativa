3. Arquitectura implementada
Se mantiene el ORM de Proyecto/Entidad/Atributo/Operacion/ParametroOperacion/Relacion como autoridad del diagrama actual y Proyecto.datos_diagrama como snapshot visual existente.
SnapshotWriter extrae el escritor anterior del consumer para reutilizarlo desde autosave y operaciones históricas; no es una segunda fuente de verdad.
DiagramHistoryOperation almacena UUID, orden, propietario, proyecto, tipo, descripción, fecha, revisiones, elementos afectados, estado y copias profundas de antes/después tomadas del ORM.
Estados: aplicada, deshecha e invalidada. Una acción nueva invalida la rama de Redo.
DiagramHistoryReceipt vincula usuario, proyecto, request_id y SHA-256 del contenido completo. Conserva el resultado confirmado incluso si se perdió el ACK. Un ID reutilizado con contenido diferente se rechaza.
DiagramEditLock conserva arrendamientos vigentes de edición por conexión, separados de los estados UML históricos. Se liberan al desconectar y expiran a los 45 segundos.
Migración aditiva: backend/modelado/migrations/0014_diagrameditlock_diagramhistoryoperation_and_more.py. Añade tres tablas, índices y restricciones únicas. Fue aplicada a PostgreSQL y probada preservando datos previos en bases de prueba.

4. Endpoints, autenticación y permisos
GET /api/modelado/proyectos/<id>/historial/: historial propio y disponibilidad, filtrados con request.user y el proyecto autorizado.
POST en la misma ruta: command, expected_revision y request_id; el servidor determina el propietario y el cambio permitido.
Las consultas usan READ; las mutaciones verifican WRITE vigente bajo bloqueo de Proyecto. No se confía en usuario_id del cliente.
El WebSocket guardar_snapshot conserva su papel de escritor del autosave. Transporta operations con snapshots de cada límite lógico.
No se exponen antes/después completos de otros usuarios, ni se envían las 50 operaciones al proveedor de IA.

5. Undo y Redo
Undo selecciona la última operación propia aplicada y compara las precondiciones del cambio contra el estado actual.
Redo selecciona la siguiente operación deshecha y vuelve a validar la transición.
Los cambios se aplican por elemento y propiedad. Las propiedades independientes posteriores se conservan.
La integridad de atributos, métodos, parámetros, referencias y relaciones impide borrar trabajo dependiente de otros colaboradores.
Una operación incompatible se rechaza con explicación y canUndo/canRedo reflejan su compatibilidad. No se salta automáticamente un conflicto ni se reemplaza el diagrama con un snapshot antiguo.
Undo/Redo cambian el estado de la entrada; no crean entradas recursivas. Sus solicitudes sí tienen recibos idempotentes.

6. Restore
Busca eliminaciones reales en las últimas 50 operaciones autorizadas: clase, atributo, método o relación.
Acepta nombres normalizados, clase contenedora, extremos de una relación, última eliminación u operation_id para desambiguar.
Si varias eliminaciones siguen siendo posibles, devuelve candidatos y pide precisar la instrucción, sin ejecutar una parte.
Recupera miembros UML, parámetros, visibilidad, tipos, valores predeterminados, referencias, coordenadas, ancho, puertos, cardinalidades, roles, navegabilidad y vértices persistidos.
El alto en este proyecto se deriva de las filas de atributos/métodos; no existía una altura persistida independiente. Se reconstruye con el contenido original.
Se reutilizan IDs históricos solo a partir de datos del servidor y después de comprobar que están libres. El cliente no puede resucitar arbitrariamente IDs positivos inexistentes.
Una clase recupera relaciones incidentes compatibles. Las que tienen extremos ausentes o duplicados se omiten con advertencias; no se inventan clases ni relaciones para completarlas.
Restore preserva acciones posteriores independientes y se registra como una nueva acción reversible.
No restaura permisos, presencia, cursores, sesiones, indicadores ni bloqueos de colaboradores. Las restricciones visuales de anclaje de relaciones son datos diferentes de esos bloqueos.

7. Persistencia, aislamiento y retención
Las operaciones pertenecen a una pareja usuario/proyecto y se consultan de nuevo al abrir el diagrama.
F5, cierre de pestaña, cierre del navegador y cierre de sesión no borran filas históricas. Angular limpia únicamente su copia local.
Abrir el diagrama solo lee el estado compartido vigente y el historial; nunca ejecuta una restauración automática.
Retención determinista: conservar las 50 filas con mayor orden lógico de cada usuario/proyecto y podar las más antiguas dentro de la transacción.
Los recibos idempotentes se mantienen aparte de esas 50 operaciones; no son una fuente de restauración y su almacenamiento crece con las solicitudes confirmadas.
No se ofrecen eliminaciones anteriores a la implementación ni descartadas por retención.

Las peticiones de IA se cancelan/inutilizan al iniciar historial, al destruir el componente o si cambian la revisión/contexto. Cada respuesta se acepta como máximo una vez.

9. Autosave, operaciones compuestas y WebSocket
Cada acción local aporta un frame inmutable antes del debounce. Un delta de IA compuesto produce un frame con todas sus mutaciones. Las notificaciones repetidas de un mismo estado se deduplican.
Un lote confirma una revisión y conserva múltiples entradas lógicas independientes.
Django obtiene antes/después autoritativos para cada frame, valida IDs, propietarios, referencias, tipos, dimensiones, relaciones e integridad, y comprueba que el último frame coincide con el snapshot final.
Diagrama, historial, revisión y recibo se confirman juntos bajo transaction.atomic y select_for_update del proyecto. Un fallo revierte el lote entero.
Los mapas de entidades, atributos, métodos, parámetros y relaciones también se aplican a todos los frames que esperan en Angular.
Undo durante debounce o guardado fuerza/espera el ACK; nunca revierte un estado local incierto.
Un timeout conserva la solicitud original para consultar/reintentar con el mismo ID y contenido. Una desconexión bloquea la reversión. Un rechazo conserva el borrador y ofrece recuperación explícita del estado remoto.
Un conflicto de revisión no se rebasa sobre trabajo remoto. Solo un ACK propio puede avanzar las revisiones de sus acciones pendientes.
Los eventos remotos no generan operaciones propias. Las vistas previas de movimiento remoto se mantienen fuera de los snapshots locales.
Las reversiones publican history.updated después del commit. Los clientes recargan el estado autoritativo; la rehidratación no registra nuevas operaciones.
La recuperación del canvas conserva el ancho y las coordenadas originales y los vértices de relaciones. La lectura REST ya no normaliza arbitrariamente '*' ni inventa asociaciones para clases intermedias huérfanas.
